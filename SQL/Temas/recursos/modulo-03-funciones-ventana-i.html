§ 1

Modelo mental

léelo antes de tocar SQL

Una window function resuelve un problema concreto: necesitas un valor que depende de otras filas — la posición dentro de un grupo, el acumulado hasta hoy, el total del grupo — pero sin perder el detalle fila por fila que GROUP BY destruye.

GROUP BY colapsa; OVER() no

GROUP BY reduce N filas a un grupo, y en el camino pierde cualquier columna que no esté en la lista de agrupación ni agregada (módulo 01, orden lógico paso 3). Una window function calcula sobre el mismo grupo pero conserva las N filas: el valor se repite o varía fila por fila según la función, y el resto de columnas de la fila original sigue disponible. Esa es toda la diferencia; el resto del módulo es consecuencia de esta frase.

Filas de entradaFilas de salidaColumnas no agregadas
GROUP BYNgrupos (≤ N)se pierden
OVER(...)NNse conservan

Anatomía mínima de OVER()

memorízalo
funcion() OVER (
    [PARTITION BY col, ...]   -- en qué "ventanas" se agrupan las filas, sin colapsarlas
    [ORDER BY col, ...]       -- orden dentro de cada ventana: define el ranking y el frame por defecto
    [ROWS|RANGE BETWEEN ...]  -- el frame: qué filas de la ventana ve la función (a fondo en el módulo 04)
)

Sin PARTITION BY, toda la tabla es una sola ventana. Sin ORDER BY, no hay ranking posible y los agregados ven toda la partición en cada fila, porque no hay frame que recortar. Con ORDER BY pero sin frame explícito, el frame por defecto cambia el resultado de un agregado — esa es la trampa central del tema 5, y el módulo 04 completo.

Qué hace el motor: un Sort antes, una pasada que no colapsa después

Internamente no hay magia: el motor primero garantiza que las filas queden ordenadas por PARTITION BY + ORDER BY — con un operador Sort explícito si ningún índice ya trae ese orden, o reutilizando el orden de un índice si existe. Luego recorre las filas ordenadas calculando el valor de la función sobre el frame vigente en cada una, sin colapsar nada. El costo real de una window function casi siempre vive en el Sort, no en la función en sí — de ahí el tema 10.

nemotecniaGROUP BY piensa en motor como "Aggregate que colapsa". OVER() piensa en motor como "Sort (si hace falta) + pasada que no colapsa".

El alias de una window function obedece la regla del módulo 01

Una window function se evalúa en la fase 5 del orden lógico, junto con el resto del SELECT — después de WHERE, GROUP BY y HAVING (fases 2 a 4) y antes de ORDER BY (fase 7). Su alias es un alias de SELECT como cualquier otro: por la regla del módulo 01 tema 3, solo es visible en ORDER BY. No puedes filtrarlo con WHERE ni con HAVING en el mismo nivel de consulta; necesitas envolver la consulta en una CTE o derivada, exactamente igual que con cualquier otro alias. Ese es el tema 2 completo.

§ 3

Ingenua vs correcta

4 comparaciones con plan

Activa el plan real (Ctrl+M en SSMS) y SET STATISTICS IO, TIME ON; antes de cada par. En las dos primeras, mira el operador Sort y el Number of Executions de la rama interna; en las otras dos, compara cuántas veces se recorre la tabla completa.

3.1 · top-N por grupo

Subconsulta correlacionada vs ROW_NUMBER

ingenua
SELECT h1.VentaId, h1.ClienteId, h1.Fecha, h1.Monto
FROM dbo.VentaHist h1
WHERE (SELECT COUNT(*) FROM dbo.VentaHist h2
       WHERE h2.ClienteId = h1.ClienteId AND h2.Monto > h1.Monto) < 2
ORDER BY h1.ClienteId, h1.Monto DESC;
correcta
WITH clasif AS (
    SELECT VentaId, ClienteId, Fecha, Monto,
           ROW_NUMBER() OVER (PARTITION BY ClienteId
                               ORDER BY Monto DESC, VentaId) AS pos
    FROM dbo.VentaHist
)
SELECT VentaId, ClienteId, Fecha, Monto
FROM clasif WHERE pos <= 2
ORDER BY ClienteId, pos;
IngenuaCorrecta
Forma del planNested Loops con subconsulta correlacionadaun Sort + una pasada de Window Spool
Number of Executions de la rama internauna vez por cada fila de VentaHist (hasta 1 000 000)0 — no hay rama repetida
Complejidad prácticacercana a O(n²) por clienteO(n log n), una sola vez
Legibilidadhay que traducir "COUNT de mayores < 2" a "top 2"literal: pos <= 2

La ingenua es la traducción literal de "dame las filas donde menos de dos sean mayores que yo" — matemáticamente correcta, pero el motor no tiene forma de saber que eso equivale a un top-N sin ejecutar la subconsulta fila por fila. El módulo 02 (tema 9) ya mostró CROSS APPLY como alternativa a esta misma subconsulta; ROW_NUMBER es la tercera forma de resolver el mismo problema, y normalmente la más barata cuando no hace falta reincidir con columnas de varias tablas por fila.

3.2 · acumulado con y sin índice de apoyo

Sort explícito vs índice compuesto que ya trae el orden

ingenua · sin índice de apoyo
-- índices existentes: IX_VentaHist_Fecha(Fecha), IX_VentaHist_Cliente(ClienteId)
-- ninguno cubre (ClienteId, Fecha) junto
SELECT ClienteId, Fecha, Monto,
       SUM(Monto) OVER (PARTITION BY ClienteId
                         ORDER BY Fecha) AS Acumulado
FROM dbo.VentaHist;
correcta · mismo query, índice nuevo
CREATE NONCLUSTERED INDEX IX_VentaHist_Cliente_Fecha
    ON dbo.VentaHist(ClienteId, Fecha) INCLUDE (Monto);

SELECT ClienteId, Fecha, Monto,
       SUM(Monto) OVER (PARTITION BY ClienteId
                         ORDER BY Fecha) AS Acumulado
FROM dbo.VentaHist;
IngenuaCorrecta
OperadorScan + Sort explícito por (ClienteId, Fecha)Index Scan sobre IX_VentaHist_Cliente_Fecha, sin Sort
Memory grantproporcional a 1 000 000 filas; riesgo de spill a tempdbmínimo
Qué cambiónada en el SQL — el índice compuesto ya entrega el orden que PARTITION BY ... ORDER BY necesita

La consulta no cambia entre ambas columnas: lo que cambia es que ahora existe un índice cuya clave es exactamente (ClienteId, Fecha), el mismo orden que pide la ventana. Esta es la comparación que el tema 10 promete: a veces la "consulta correcta" no es una reescritura, es un índice.

3.3 · porcentaje por grupo

Subconsulta correlacionada vs SUM() OVER(PARTITION BY)

ingenua
SELECT VentaId, ClienteId, Canal, Monto,
       CAST(Monto AS decimal(14,4))
         / (SELECT SUM(h2.Monto) FROM dbo.VentaHist h2
            WHERE h2.Canal = h1.Canal) AS PctCanal
FROM dbo.VentaHist h1;
correcta
SELECT VentaId, ClienteId, Canal, Monto,
       CAST(Monto AS decimal(14,4))
         / SUM(Monto) OVER (PARTITION BY Canal) AS PctCanal
FROM dbo.VentaHist;
IngenuaCorrecta
Forma del plansubconsulta correlacionada por Canal, reevaluada por filaun Sort/Stream por Canal, agregado calculado una vez por partición
Trabajo repetidoel mismo SUM por canal se recalcula una y otra vezse calcula una sola vez por valor de Canal y se reparte a cada fila

Es el mismo error del módulo 01 (división entera silenciosa, catálogo de errores #13) más un problema nuevo: aquí el numerador y el denominador sí están bien tipados con CAST, pero el cómo se obtiene el denominador es lo caro. Cuatro valores distintos de Canal no justifican recalcular la suma un millón de veces.

3.4 · cuartiles

Cuatro consultas con OFFSET/FETCH vs un NTILE

ingenua
SELECT ClienteId, LimiteCredito, 1 AS Cuartil
FROM dbo.Cliente ORDER BY LimiteCredito DESC
OFFSET 0 ROWS FETCH NEXT 3 ROWS ONLY
UNION ALL
SELECT ClienteId, LimiteCredito, 2
FROM dbo.Cliente ORDER BY LimiteCredito DESC
OFFSET 3 ROWS FETCH NEXT 3 ROWS ONLY
UNION ALL
SELECT ClienteId, LimiteCredito, 3
FROM dbo.Cliente ORDER BY LimiteCredito DESC
OFFSET 6 ROWS FETCH NEXT 3 ROWS ONLY
UNION ALL
SELECT ClienteId, LimiteCredito, 4
FROM dbo.Cliente ORDER BY LimiteCredito DESC
OFFSET 9 ROWS FETCH NEXT 3 ROWS ONLY;
correcta
SELECT ClienteId, LimiteCredito,
       NTILE(4) OVER (ORDER BY LimiteCredito DESC) AS Cuartil
FROM dbo.Cliente;
IngenuaCorrecta
Operadorcuatro Sorts independientes (uno por rama) + Concatenationun solo Sort
Se rompe si...cambia el número de filas: los OFFSET quedan mal a manonunca: NTILE se recalcula solo

Cada rama de la UNION ALL ordena toda la tabla otra vez, porque OFFSET/FETCH exige el resultado ya ordenado antes de recortar (orden lógico, paso 8). Cuatro Sorts del mismo conjunto por el costo de uno, y encima frágil: si mañana hay 13 clientes en vez de 12, los cuatro OFFSET quedan desalineados y nadie se entera hasta que alguien audita los cuartiles a mano.

§ 4

Errores comunes

12 · resultados silenciosamente incorrectos

Casi ninguno lanza un error de sintaxis: producen un número que parece razonable y no lo es. El caso mínimo de cada uno se reproduce en segundos sobre el dataset del módulo.

1 · RANK en un contrato de "exactamente top-N"

SELECT id, puntos, RANK() OVER (ORDER BY puntos DESC) AS rk
FROM (VALUES (1,100),(2,90),(3,90),(4,90),(5,70)) AS t(id,puntos);
-- filtrar rk <= 2 devuelve 4 filas (1,2,3,4), no 2

fix · si el requisito es "exactamente N filas por grupo", usa ROW_NUMBER con un desempate único (tema 7). Usa RANK solo cuando el contrato es "todas las filas empatadas en la posición N inclusive".

2 · ORDER BY dentro de OVER() convierte un total en un acumulado

SUM(Cantidad*PrecioUnit) OVER (PARTITION BY ClienteId ORDER BY Fecha) AS Total
-- no es el total del cliente: es el acumulado hasta esa fecha

fix · si necesitas el total de la partición y de todos modos quieres el ORDER BY (por ejemplo para mostrar filas ordenadas), fuerza ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING, o quita el ORDER BY del OVER() y ponlo en la consulta externa. Ver tema 5.

3 · Filtrar la ventana con WHERE en el mismo nivel

-- Msg 4108: Windowed functions can only appear in the SELECT or ORDER BY clauses
SELECT ClienteId, VentaId
FROM dbo.Venta
WHERE ROW_NUMBER() OVER (PARTITION BY ClienteId ORDER BY Fecha) = 1;

fix · envuelve en CTE o derivada (tema 2); en Databricks/Snowflake, QUALIFY evita el envoltorio (tema 8).

4 · NULLs en la columna de PARTITION BY forman su propia partición

fix · PARTITION BY Ciudad junta a todos los clientes con Ciudad NULL en una sola ventana, como si compartieran ciudad. Si esa no es la regla de negocio, filtra los NULL antes o normalízalos con COALESCE explícitamente — decide, no heredes el comportamiento por defecto.

5 · NTILE reparte los empates de forma arbitraria entre buckets vecinos

fix · en el tema 3, los clientes 1 y 2 (mismo LimiteCredito) caen en cuartiles distintos porque NTILE reparte por posición, no por valor. Si el requisito es "mismo valor, mismo bucket siempre", NTILE no es la herramienta: define los cortes con CASE WHEN sobre el valor.

6 · ROW_NUMBER sin desempate único: la fila "ganadora" cambia entre ejecuciones

fix · termina siempre el ORDER BY de la ventana con una columna única por partición. Es el mismo problema del módulo 01, catálogo de errores #12, aplicado ahora a deduplicación de cargas (tema 4).

7 · DISTINCT después de numerar no elimina nada

SELECT DISTINCT ClienteId, VentaId,
       ROW_NUMBER() OVER (PARTITION BY ClienteId ORDER BY Fecha) AS rn
FROM dbo.Venta;  -- rn es distinto en cada fila: DISTINCT no colapsa nada

fix · si la intención era deduplicar, el ROW_NUMBER + filtro del tema 4 ya lo hace; el DISTINCT sobra. Si de verdad necesitas deduplicar por otras columnas, hazlo antes de numerar, no después.

8 · COUNT(*) OVER() vs COUNT(columna) OVER()

COUNT(Descuento) OVER (PARTITION BY ClienteId) -- cuenta solo ventas CON descuento
COUNT(*)         OVER (PARTITION BY ClienteId) -- cuenta todas las ventas del cliente

fix · el mismo problema del módulo 01 (catálogo de errores #5), ahora dentro de una ventana: decide explícitamente cuál de las dos preguntas estás haciendo.

9 · Olvidar el DESC cuando "más alto" debería ser el puesto 1

fix · RANK() OVER (ORDER BY Total) sin DESC no falla: solo invierte el ranking sin avisar. Verifica siempre el primer y el último puesto contra un caso conocido antes de confiar en un ranking nuevo.

10 · Dos OVER() con particiones de distinta granularidad, mezclados en un mismo % que "debería sumar 100"

fix · si vas a mostrar PctCliente y PctCategoria lado a lado, corre una consulta de control que verifique SUM(PctTotal) = 1 por cada agrupación antes de publicar el reporte — no lo asumas por simetría visual.

11 · Un JOIN que multiplica filas antes del OVER() infla todos los agregados de ventana

fix · si un SUM() OVER() sale "demasiado grande", sospecha primero de un join que multiplicó filas antes de llegar a la ventana — no del propio OVER(). Ver módulo 02, tema 10 (diagnóstico de explosión de filas por granularidad distinta).

12 · Copiar QUALIFY literal de un script de Databricks a T-SQL

fix · error de sintaxis inmediato: la palabra clave no existe en SQL Server ni en PostgreSQL. Todo QUALIFY se traduce al patrón CTE + WHERE de los temas 4 y 8; no hay atajo de sintaxis.

§ 6

Mini-proyecto

reporte de ventas con dedup, ranking y participación

La carga diaria del módulo trae reprocesos y una corrección real mezclados (§0). El reporte debe deduplicar antes de calcular nada, y cada número tiene que cuadrar con un control independiente. Siete criterios de aceptación ejecutables, incluidos uno de idempotencia y uno que verifica la corrección de la venta 18.

Entregable

Un script que produzca dbo.ReporteVentasAbril, una fila por cliente con ventas ese mes:

ColumnaContenido
ClienteId, Nombreidentificación del cliente
TotalBrutosuma de Cantidad*PrecioUnit ya deduplicada
RankingClienteRANK por TotalBruto DESC: los empates comparten puesto
PctTotalparticipación del cliente sobre el total general (decimal 0-1)
ProductoTopId, ProductoTopNombre, UnidadesProductoTopproducto con más unidades compradas por ese cliente, con desempate estable

Reglas obligatorias

Criterios de aceptación

cada consulta debe devolver OK
-- AC1 · una fila por cliente, sin duplicados
SELECT CASE WHEN COUNT(*) = COUNT(DISTINCT ClienteId) THEN 'OK' ELSE 'FALLA' END
FROM dbo.ReporteVentasAbril;

-- AC2 · cuadre de clientes: coincide con el universo deduplicado
;WITH dedup AS (
    SELECT *, ROW_NUMBER() OVER (PARTITION BY VentaId
                                  ORDER BY FechaCarga DESC, CargaId DESC) AS rn
    FROM dbo.VentaCargaDiaria
)
SELECT CASE WHEN (SELECT COUNT(*) FROM dbo.ReporteVentasAbril)
               = (SELECT COUNT(DISTINCT ClienteId) FROM dedup WHERE rn = 1)
            THEN 'OK' ELSE 'FALLA' END;

-- AC3 · los porcentajes suman 1 (con tolerancia de redondeo)
SELECT CASE WHEN ABS(SUM(PctTotal) - 1) < 0.0005 THEN 'OK' ELSE 'FALLA' END
FROM dbo.ReporteVentasAbril;

-- AC4 · control cruzado del total: mismo número calculado con MAX en vez de ROW_NUMBER
;WITH dedup AS (
    SELECT *, ROW_NUMBER() OVER (PARTITION BY VentaId
                                  ORDER BY FechaCarga DESC, CargaId DESC) AS rn
    FROM dbo.VentaCargaDiaria
), control AS (
    SELECT ClienteId, SUM(Cantidad*PrecioUnit) AS TotalControl
    FROM dedup WHERE rn = 1 GROUP BY ClienteId
)
SELECT CASE WHEN NOT EXISTS (
            SELECT 1 FROM dbo.ReporteVentasAbril r
            JOIN control c ON c.ClienteId = r.ClienteId
            WHERE r.TotalBruto <> c.TotalControl)
            THEN 'OK' ELSE 'FALLA' END;

-- AC5 · la corrección de la venta 18 quedó aplicada (Cantidad = 2, no 1)
SELECT CASE WHEN TotalBruto = 2 * 300.00 THEN 'OK' ELSE 'FALLA' END
FROM dbo.ReporteVentasAbril WHERE ClienteId = 10;

-- AC6 · el ranking no inventa huecos más allá de los que genera un empate real
SELECT CASE WHEN COUNT(DISTINCT RankingCliente) = COUNT(DISTINCT TotalBruto)
            THEN 'OK' ELSE 'FALLA' END
FROM dbo.ReporteVentasAbril;

-- AC7 · idempotencia
SELECT CASE WHEN NOT EXISTS (SELECT * FROM dbo.ReporteVentasAbril
                             EXCEPT SELECT * FROM dbo.ReporteVentasAbril_Snapshot)
             AND NOT EXISTS (SELECT * FROM dbo.ReporteVentasAbril_Snapshot
                             EXCEPT SELECT * FROM dbo.ReporteVentasAbril)
            THEN 'OK' ELSE 'FALLA' END;

AC4 es el más importante de leer: no compara el reporte contra sí mismo, sino contra una segunda deducción del mismo número escrita de forma independiente. Si ambas coinciden, el error de haber deduplicado mal en un solo lugar deja de ser invisible.

Pistas de diseño

  • El dedup es una sola CTE que se reutiliza (o se materializa en una tabla temporal) para todo el reporte: total, ranking y producto top deben partir del mismo conjunto ya deduplicado. Calcularlo dos veces con criterios ligeramente distintos es la forma más común de que AC4 falle.
  • El producto top por cliente es un segundo ROW_NUMBER() OVER (PARTITION BY ClienteId ORDER BY SUM(Cantidad) DESC, ProductoId) sobre una agregación por (ClienteId, ProductoId) — dos pasadas de ventana encadenadas, como en el ejercicio 6.
  • PctTotal necesita el total general una sola vez: SUM(TotalBruto) OVER () sobre la tabla ya agregada por cliente, no una subconsulta repetida (comparación 3.3).
