§ 1

Modelo mental

léelo antes de tocar SQL

Todo el módulo se reduce a una sola pregunta que hay que hacerse antes de escribir el join: para una fila de A, ¿con cuántas de B puede hacer match? Si no sabes la respuesta, no puedes predecir el tamaño ni la corrección del resultado.

El FROM produce, el resto filtra

El paso 1 del orden lógico (ver módulo 01, tema 2) —el FROM, que incluye el JOIN y su ON— construye el conjunto de filas de trabajo. Todo tipo de join (INNER, LEFT, RIGHT, FULL, CROSS) es una variación de la misma idea: partir del producto cartesiano de las dos tablas y decidir, según el ON, cuáles filas sobreviven y qué hacer con las que no encontraron pareja. Esa segunda parte —qué pasa con los que no matchean— es la única diferencia real entre los cinco tipos.

La pregunta de cardinalidad

Relación entre las clavesPara 1 fila de ARiesgo
1 a 10 o 1 fila de Bninguno: el join nunca crece el resultado
1 a N0, 1 o varias filas de Bel resultado crece; correcto si lo esperabas, bug si no
N a M (join directo entre dos tablas 1:N de un mismo padre)el producto de ambas cardinalidadesfan trap — tema 10

Antes de confiar en cualquier SUM/COUNT posterior a un join, contesta esa pregunta para cada par de tablas involucradas. Si la respuesta es "no estoy seguro", el join necesita DISTINCT, agregación previa, o convertirse en EXISTS/APPLY — que es justo la decisión que estructura los temas 3, 8 y 10.

JOIN junta valores; EXISTS y APPLY hacen otra cosa

  • JOIN combina dos conjuntos de filas de forma simétrica: ninguna de las dos tablas "sabe" de la otra hasta que se evalúa el ON.
  • EXISTS/NOT EXISTS no traen columnas del lado derecho: solo preguntan presencia. Por construcción, nunca pueden multiplicar filas del lado externo, sin importar cuántas coincidencias existan.
  • APPLY es procedural en su planteamiento: para cada fila de la izquierda, ejecuta una expresión de tabla que puede referenciar esa fila — algo que un JOIN corriente no puede hacer, porque sus dos lados se evalúan como conjuntos independientes antes de compararse.
regla operativaSi la pregunta es "¿existe?", usa EXISTS. Si la pregunta es "tráeme el/los que correspondan a esta fila específica", usa APPLY. Si la pregunta es "combina estos dos conjuntos completos", usa JOIN — y verifica la cardinalidad antes de confiar en cualquier agregado posterior.

Lo que el optimizador puede y no puede reordenar

Para INNER y CROSS, el optimizador puede reordenar libremente las tablas del FROM porque el resultado final es el mismo sin importar el orden de evaluación. Para OUTER JOIN el orden sí importa para la corrección (un LEFT no es lo mismo hacia un lado que hacia el otro), así que el optimizador conserva la semántica pedida — aunque sigue siendo libre de elegir qué algoritmo físico (Nested Loops, Hash Match, Merge Join) usar para ejecutarlo; ese detalle es del módulo 09.

3.1 · ON vs WHERE

LEFT JOIN degradado a INNER por el WHERE

ingenua
SELECT c.ClienteId, c.Nombre, v.VentaId
FROM dbo.Cliente c
LEFT JOIN dbo.Venta v ON v.ClienteId = c.ClienteId
WHERE v.Canal = 'WEB';
correcta
SELECT c.ClienteId, c.Nombre, v.VentaId
FROM dbo.Cliente c
LEFT JOIN dbo.Venta v ON v.ClienteId = c.ClienteId
                     AND v.Canal = 'WEB';
IngenuaCorrecta
Operador en el planInner Join — el optimizador simplifica el LEFT porque el WHERE hace imposible que sobreviva una fila con NULLLeft Outer Join, tal como se pidió
Filas de salidasolo clientes con venta WEB12 filas: todos los clientes, NULL donde no hubo venta WEB
Resultadoincorrecto si la pregunta era "todos los clientes"correcto

El costo aquí es secundario al resultado: un Inner Join suele ser más barato que un Left Outer Join, pero ese ahorro es irrelevante si la pregunta de negocio exigía preservar a todos los clientes. La lección no es de rendimiento: el operador del plan te dice, sin ambigüedad, si tu LEFT sigue siendo un LEFT.

3.2 · anti-join a escala

NOT IN vs NOT EXISTS sobre teléfonos con NULL reales

ingenua
SELECT COUNT(*)
FROM dbo.ClienteTelefonoMasivo t1
WHERE t1.Telefono NOT IN (
    SELECT Telefono FROM dbo.ClienteTelefonoMasivo WHERE ClienteId % 97 = 0
);   -- ese subconjunto SIEMPRE contiene algún Telefono NULL (ClienteId % 5 = 0) -> 0 filas
correcta
SELECT COUNT(*)
FROM dbo.ClienteTelefonoMasivo t1
WHERE NOT EXISTS (
    SELECT 1 FROM dbo.ClienteTelefonoMasivo t2
    WHERE t2.Telefono = t1.Telefono AND t2.ClienteId % 97 = 0
);
Ingenua (NOT IN)Correcta (NOT EXISTS)
Resultado con NULL en el subconjunto derecho0 filas, siempreel conjunto real de no-coincidencias
Uso del índice sobre Telefonodegradado: necesita una rama adicional para descartar el caso NULLSeek directo, sin rama adicional
OperadorAnti Semi Join con comprobación de NULL extraLeft Anti Semi Join limpio

A esta escala el problema no es solo "el resultado está mal": la semántica de NOT IN sobre una columna anulable obliga al optimizador a cargar una comprobación adicional de NULL en cada fila candidata, lo que le impide beneficiarse igual de un índice simple sobre Telefono.

3.3 · non-equi join sin desempate

Atribución de campaña que duplica ventas

ingenua
SELECT v.VentaId, ca.CampaniaId
FROM dbo.Venta v
JOIN dbo.Campania ca
     ON (ca.Canal = v.Canal OR ca.Canal IS NULL)
    AND v.Fecha >= ca.FechaInicio AND v.Fecha < DATEADD(day,1,ca.FechaFin);
-- 21 filas para 20 ventas: la venta 8 aparece dos veces
correcta
SELECT v.VentaId, x.CampaniaId
FROM dbo.Venta v
CROSS APPLY (
    SELECT TOP (1) ca.CampaniaId
    FROM dbo.Campania ca
    WHERE (ca.Canal = v.Canal OR ca.Canal IS NULL)
      AND v.Fecha >= ca.FechaInicio AND v.Fecha < DATEADD(day,1,ca.FechaFin)
    ORDER BY ca.PctDescuento DESC, ca.CampaniaId
) x;
-- 20 filas: una por venta, siempre
IngenuaCorrecta
Cardinalidad de salidavariable — depende de cuántas campañas coincidanfija: una fila por venta, por construcción
OperadorNested Loops que emite una fila por cada coincidenciaNested Loops + Top, corta en la primera fila ordenada
Riesgo si alimenta un SUM aguas abajoalto: monto duplicado en las fechas de solapeninguno

La diferencia de costo entre ambas es mínima — las dos usan Nested Loops. La diferencia real es de garantía estructural: el TOP (1) dentro del APPLY hace que la cardinalidad de salida sea imposible de romper, incluso si mañana se agrega otra campaña que se solape.

3.4 · subconsultas repetidas vs una sola APPLY

Tres subconsultas correlacionadas vs un solo CROSS APPLY

ingenua · tres pasadas independientes
SELECT v1.ClienteId, v1.Fecha,
  (SELECT MAX(v2.Fecha) FROM dbo.VentaHist v2
     WHERE v2.ClienteId = v1.ClienteId AND v2.Fecha < v1.Fecha)                        AS FechaAnt,
  (SELECT TOP(1) v3.Monto FROM dbo.VentaHist v3
     WHERE v3.ClienteId = v1.ClienteId AND v3.Fecha < v1.Fecha ORDER BY v3.Fecha DESC) AS MontoAnt,
  (SELECT TOP(1) v4.Canal FROM dbo.VentaHist v4
     WHERE v4.ClienteId = v1.ClienteId AND v4.Fecha < v1.Fecha ORDER BY v4.Fecha DESC) AS CanalAnt
FROM dbo.VentaHist v1;
correcta · una sola APPLY
SELECT v1.ClienteId, v1.Fecha, x.Fecha AS FechaAnt, x.Monto AS MontoAnt, x.Canal AS CanalAnt
FROM dbo.VentaHist v1
OUTER APPLY (
    SELECT TOP (1) v2.Fecha, v2.Monto, v2.Canal
    FROM dbo.VentaHist v2
    WHERE v2.ClienteId = v1.ClienteId AND v2.Fecha < v1.Fecha
    ORDER BY v2.Fecha DESC
) x;
IngenuaCorrecta
Búsquedas correlacionadas por fila3 (una por subconsulta escalar)1
Lecturas sobre IX_VentaHist_Clientetriplicadasuna sola vez, reutilizada
Consistencia entre columnasen teoría podrían no venir de la misma fila "anterior" si algo desincroniza los criterios de empategarantizada: las tres vienen de la misma fila física

Cada subconsulta escalar adicional en el SELECT es, para el optimizador, otra ejecución correlacionada completa. APPLY devuelve una tabla, no un escalar: una sola ejecución basta para traer cuantas columnas necesites de la misma fila relacionada.

3.5 · explosión de filas a escala

Join directo entre dos tablas hijas vs agregación previa

ingenua
SELECT cm.ClienteId, SUM(vh.Monto) AS Total
FROM dbo.ClienteMasivo cm
JOIN dbo.VentaHist vh             ON vh.ClienteId = cm.ClienteId
JOIN dbo.ClienteTelefonoMasivo tm ON tm.ClienteId = cm.ClienteId
GROUP BY cm.ClienteId;
correcta
SELECT cm.ClienteId, ISNULL(vt.Total,0) AS Total, ISNULL(tt.NumTelefonos,0) AS NumTelefonos
FROM dbo.ClienteMasivo cm
LEFT JOIN (SELECT ClienteId, SUM(Monto) AS Total FROM dbo.VentaHist GROUP BY ClienteId) vt
       ON vt.ClienteId = cm.ClienteId
LEFT JOIN (SELECT ClienteId, COUNT(*) AS NumTelefonos FROM dbo.ClienteTelefonoMasivo GROUP BY ClienteId) tt
       ON tt.ClienteId = cm.ClienteId;
IngenuaCorrecta
Filas procesadas antes de agregarvarios millones (producto por cliente con 2 teléfonos)1 000 000 + ~375 000, cada una agregada por separado primero
Total resultanteinflado donde el cliente tiene 2 teléfonoscorrecto siempre
Operador dominanteHash Match masivo antes de poder agregar nadados Stream/Hash Aggregate pequeños + un join final de "uno a lo sumo uno"

La versión correcta no solo da el número correcto: procesa cada tabla hija una vez, a su propia granularidad, antes de combinarlas. La ingenua paga el costo del producto cartesiano completo y encima entrega un número que hay que volver a auditar.

§ 4

Errores silenciosos

12 casos · todos ejecutan sin error

Ninguno lanza excepción. El reporte sale, el proceso termina en verde, y el número o el conjunto de filas está mal.

1 · LEFT JOIN degradado a INNER por el WHERE

fix · mover el predicado del lado opcional al ON. Ver tema 2 y comparación 3.1. (Ver también módulo 01, catálogo de errores, caso 15.)

2 · NOT IN con columna anulable → conjunto vacío

fix · NOT EXISTS, o filtrar el NULL explícitamente en la subconsulta. Ver tema 4 y comparación 3.2.

3 · Falta de DISTINCT tras un INNER JOIN 1:N

SELECT COUNT(*) FROM dbo.Cliente c JOIN dbo.Venta v ON v.ClienteId = c.ClienteId;  -- 20, no 10 clientes

fix · si la pregunta era "cuántos clientes", usa COUNT(DISTINCT c.ClienteId) o reescribe con EXISTS.

4 · Fan trap: join directo entre dos tablas hijas sin agregar antes

fix · agregar cada hija a nivel del padre antes de unir. Ver tema 10 y comparación 3.5.

5 · FULL JOIN + WHERE en cualquiera de los dos lados anula la mitad preservada

SELECT c.ClienteId, e.Origen
FROM dbo.Cliente c
FULL JOIN dbo.ClienteExterno e ON e.Cedula = c.Cedula
WHERE e.Origen = 'BURO';   -- descarta TODOS los clientes que no están en el buró

fix · mueve el predicado al ON, o exprésalo completo: WHERE e.Origen = 'BURO' OR e.Cedula IS NULL.

6 · CROSS JOIN accidental por olvidar el predicado de unión

SELECT * FROM dbo.Cliente, dbo.Venta;  -- sintaxis de coma sin WHERE de unión: 12 x 20 = 240 filas

fix · usa siempre JOIN … ON explícito; nunca la sintaxis de coma implícita, ni siquiera con la intención de agregar el WHERE después.

7 · Self join sin exclusión de identidad

SELECT v1.VentaId, v2.VentaId
FROM dbo.Venta v1 JOIN dbo.Venta v2 ON v1.ClienteId = v2.ClienteId;
-- cada fila matchea consigo misma: v1.VentaId = v2.VentaId también cuenta

fix · agrega v1.VentaId <> v2.VentaId (o < si además quieres evitar el par simétrico). Ver tema 5.

8 · Self join sin desempate de dirección: cada par sale dos veces

fix · t1.Id < t2.Id en vez de <>. Ver tema 7b.

9 · Rango con límite mal cerrado en un non-equi join de fechas

-- BETWEEN inclusivo en ambos extremos: una campaña que termina el mismo día que otra empieza
-- puede atribuir la venta de ese día a las dos
... v.Fecha BETWEEN ca.FechaInicio AND ca.FechaFin ...

fix · usa un rango semiabierto: v.Fecha >= ca.FechaInicio AND v.Fecha < DATEADD(day,1,ca.FechaFin). Ver tema 6.

10 · TOP (1) sin ORDER BY determinista dentro de un APPLY

fix · termina siempre el ORDER BY con una columna única (como en la comparación 3.3). Sin eso, "el top" puede cambiar entre ejecuciones idénticas.

11 · CROSS APPLY donde se necesitaba OUTER APPLY

fix · si la fila izquierda debe sobrevivir aunque el lado derecho no produzca nada, usa OUTER APPLY. Ver tema 8.

12 · Colación distinta en el ON de un join

fix · fija la colación explícitamente en el ON cuando el negocio exige comparar sin distinguir acentos o mayúsculas. Ver módulo 01, tema 8.

§ 6

Mini-proyecto

atribución de ventas a campañas sin duplicar filas

Construye una tabla de atribución que resuelva la ambigüedad de rangos del tema 6 con una garantía estructural de cardinalidad, y verifícala con siete criterios ejecutables, incluido uno de idempotencia y uno sobre el calendario del tema 7.

Entregable

Una fila por cada venta de dbo.Venta en dbo.VentaAtribuida, con la campaña vigente de mayor descuento si hay más de una, o NULL si ninguna aplica.

T-SQL · script objetivo
DROP TABLE IF EXISTS dbo.VentaAtribuida;
GO
SELECT v.VentaId, v.ClienteId, v.Fecha, v.Canal,
       v.Cantidad*v.PrecioUnit - ISNULL(v.Descuento,0) AS MontoNeto,
       x.CampaniaId, x.PctDescuento
INTO dbo.VentaAtribuida
FROM dbo.Venta v
OUTER APPLY (
    SELECT TOP (1) ca.CampaniaId, ca.PctDescuento
    FROM dbo.Campania ca
    WHERE (ca.Canal = v.Canal OR ca.Canal IS NULL)
      AND v.Fecha >= ca.FechaInicio AND v.Fecha < DATEADD(day,1,ca.FechaFin)
    ORDER BY ca.PctDescuento DESC, ca.CampaniaId
) x;
GO

Reglas obligatorias

Criterios de aceptación

cada consulta debe devolver OK
-- AC1 · Sin fan-out: mismo número de filas que dbo.Venta
SELECT CASE WHEN (SELECT COUNT(*) FROM dbo.VentaAtribuida) = (SELECT COUNT(*) FROM dbo.Venta)
            THEN 'OK' ELSE 'FALLA' END;

-- AC2 · Ninguna VentaId duplicada
SELECT CASE WHEN COUNT(*) = COUNT(DISTINCT VentaId) THEN 'OK' ELSE 'FALLA' END
FROM dbo.VentaAtribuida;

-- AC3 · La venta 8 (2023-06-01, AGENCIA) se atribuye a la campaña de mayor descuento (4, 8%)
SELECT CASE WHEN CampaniaId = 4 THEN 'OK' ELSE 'FALLA' END
FROM dbo.VentaAtribuida WHERE VentaId = 8;

-- AC4 · La venta 3 (2023-03-05, Canal NULL) no tiene catch-all vigente ese día -> NULL
SELECT CASE WHEN CampaniaId IS NULL THEN 'OK' ELSE 'FALLA' END
FROM dbo.VentaAtribuida WHERE VentaId = 3;

-- AC5 · Completitud: todas las ventas del origen están representadas
SELECT CASE WHEN COUNT(*) = 0 THEN 'OK' ELSE 'FALLA' END
FROM dbo.Venta v
WHERE NOT EXISTS (SELECT 1 FROM dbo.VentaAtribuida va WHERE va.VentaId = v.VentaId);

-- AC6 · Idempotencia (guarda un snapshot antes de reejecutar el script y compara en ambas direcciones)
SELECT CASE WHEN NOT EXISTS (SELECT * FROM dbo.VentaAtribuida EXCEPT SELECT * FROM dbo.VentaAtribuida_Snapshot)
             AND NOT EXISTS (SELECT * FROM dbo.VentaAtribuida_Snapshot EXCEPT SELECT * FROM dbo.VentaAtribuida)
            THEN 'OK' ELSE 'FALLA' END;

-- AC7 · Días sin venta en 2023 (tema 7c)
SELECT CASE WHEN COUNT(*) = 351 THEN 'OK' ELSE 'FALLA' END
FROM dbo.Calendario cal
LEFT JOIN (SELECT CAST(Fecha AS date) AS Fecha FROM dbo.Venta
           WHERE Fecha >= '2023-01-01' AND Fecha < '2024-01-01'
           GROUP BY CAST(Fecha AS date)) d ON d.Fecha = cal.Fecha
WHERE cal.Fecha BETWEEN '2023-01-01' AND '2023-12-31' AND d.Fecha IS NULL;

AC6 reutiliza el idioma EXCEPT en ambas direcciones del mini-proyecto del módulo 01 — es null-safe y compara filas completas, exactamente lo que hace falta para probar "esto no cambió".

Pistas de diseño

  • El límite superior del rango de fecha debe ser exclusivo (< DATEADD(day,1,FechaFin)), no un BETWEEN inclusivo — es el error catalogado #9.
  • El ORDER BY PctDescuento DESC, CampaniaId dentro del APPLY es lo único que garantiza AC3 y AC6 a la vez.
  • AC4 falla si tu ON usa ca.Canal = v.Canal sin el OR ca.Canal IS NULL — revisa el tema 6.
