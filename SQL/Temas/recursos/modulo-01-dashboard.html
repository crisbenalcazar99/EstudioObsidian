§ 1

Modelo mental

léelo antes de tocar SQL

Todo el módulo se sostiene sobre una distinción: el orden lógico define qué es el resultado correcto; el plan define cómo se obtiene. Mezclarlos es el origen de casi todas las confusiones que siguen.

Dos órdenes que no hay que confundir

Qué defineQuién lo fija¿Cambia?
Orden lógicoQué debe devolver la consultaEl estándar SQLNo. Es un contrato.
Orden físicoCómo se obtiene (el plan)El optimizadorSí, en cada ejecución.

El orden lógico no es una receta de ejecución. El optimizador puede evaluar el WHERE antes del JOIN, empujar un predicado dentro de una vista o saltarse una tabla entera, siempre que el resultado sea el mismo que produciría el orden lógico. Esa libertad es exactamente lo que habilita el predicate pushdown y todas las reescrituras de los módulos 09 y 10.

regla operativaRazonas la corrección con el orden lógico. Razonas el costo con el plan. Nunca al revés.

Qué hace el motor antes de optimizar

  • 1. Parsing — validación sintáctica. Aquí muere SELCT.
  • 2. Binding / algebrización — resolución de nombres, tipos, colaciones y permisos. Aquí muere WHERE Total > 100 cuando Total es un alias del SELECT: no es un error de ejecución ni de rendimiento, es de resolución de nombres.
  • 3. Simplificación — árbol de operadores relacionales, eliminación de joins redundantes y contradicciones.
  • 4. Optimización — transformaciones algebraicas y costeo con estadísticas.
  • 5. Ejecución — el plan corre como un pipeline de operadores.

Nemotecnia: el orden lógico vive en la fase 2; el orden físico vive en la fase 4.

La tabla es un multiconjunto, no un archivo

Una tabla es un conjunto en teoría y un multiconjunto en SQL: admite duplicados y no tiene orden intrínseco. Ni el orden de inserción, ni el del índice clustered, ni el del archivo son un orden garantizado. El orden solo existe cuando lo pides con ORDER BY en la consulta más externa. Esta única frase explica el tema 9 completo y la mitad de los bugs de producción del módulo.

El orden lógico canónico

memorízalo
(1) FROM        -> incluye JOIN y ON: produce el conjunto de filas de trabajo
(2) WHERE       -> filtra filas individuales
(3) GROUP BY    -> colapsa filas en grupos
(4) HAVING      -> filtra grupos
(5) SELECT      -> proyecta: aquí y solo aquí nacen los alias de salida
(6) DISTINCT    -> elimina duplicados del resultado ya proyectado
(7) ORDER BY    -> ordena el resultado
(8) OFFSET/FETCH (o TOP) -> recorta el resultado ya ordenado
  • SELECT es el paso 5: por eso WHERE, GROUP BY y HAVING no ven los alias de salida en T-SQL.
  • ORDER BY es el paso 7: por eso sí los ve. Es la única cláusula que opera sobre el resultado proyectado.
  • DISTINCT (6) va después de SELECT (5): por eso SELECT DISTINCT … ORDER BY <columna no proyectada> es un error — esa columna se perdió en la proyección.

Semántica "todo a la vez"

Dentro de una misma cláusula todas las expresiones se evalúan conceptualmente en simultáneo. No hay orden de izquierda a derecha ni cortocircuito garantizados.

T-SQL
-- No compila: c1 no existe todavía cuando se evalúa c2
SELECT 1 AS c1, c1 + 1 AS c2;

-- Puede fallar con "Divide by zero" pese al primer predicado:
-- el orden de evaluación del AND no es contractual
SELECT * FROM dbo.Venta WHERE Cantidad <> 0 AND (100 / Cantidad) > 5;

-- La forma que sí garantiza el orden es CASE
SELECT * FROM dbo.Venta WHERE CASE WHEN Cantidad = 0 THEN 0 ELSE 100 / Cantidad END > 5;

En PostgreSQL y Spark aplica lo mismo: el AND no garantiza orden de evaluación; CASE sí.

§ 3

Ingenua vs correcta

4 comparaciones con plan

Activa el plan real (Ctrl+M en SSMS) y SET STATISTICS IO, TIME ON; antes de cada par. Lo que importa no es el tiempo del reloj sino qué operador aparece y cuántas filas toca.

3.1 · función sobre la columna

Función sobre la columna → scan

ingenua
SELECT COUNT(*), SUM(Monto)
FROM dbo.VentaHist
WHERE YEAR(Fecha) = 2023;
correcta
SELECT COUNT(*), SUM(Monto)
FROM dbo.VentaHist
WHERE Fecha >= '2023-01-01'
  AND Fecha <  '2024-01-01';

El índice está ordenado por Fecha, no por YEAR(Fecha). Cualquier función sobre la columna destruye la correspondencia entre el orden del índice y el del predicado. Y la estimación mala es tan grave como el scan: propaga elecciones de join y reservas de memoria equivocadas por todo el plan.

3.2 · conversión implícita

Conversión implícita del lado de la columna

ingenua · parámetro nvarchar
DECLARE @ced_n nvarchar(13) = N'0000123456001';
SELECT Nombre FROM dbo.ClienteMasivo
WHERE Cedula = @ced_n;
correcta · mismo tipo que la columna
DECLARE @ced_v varchar(13) = '0000123456001';
SELECT Nombre FROM dbo.ClienteMasivo
WHERE Cedula = @ced_v;
  • En las propiedades del operador aparece CONVERT_IMPLICIT(nvarchar(13),[Cedula],0) aplicado a la columna.
  • El plan trae el warning PlanAffectingConvert (triángulo amarillo sobre el SELECT en SSMS).
  • Con colación Windows verás probablemente un Seek con GetRangeThroughConvert: menos malo, pero con estimación degradada. Con colación SQL_* heredada verás un Index Scan de 500 000 filas para devolver una. Por eso el mismo código vuela en un servidor y se arrastra en otro.
cazar el problema en todo el caché de planes
SELECT TOP (50) qs.execution_count, SUBSTRING(t.text, 1, 300) AS consulta
FROM sys.dm_exec_query_stats qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) t
CROSS APPLY sys.dm_exec_query_plan(qs.plan_handle) p
WHERE CAST(p.query_plan AS nvarchar(max)) LIKE '%PlanAffectingConvert%'
ORDER BY qs.execution_count DESC;

3.3 · anti-join

NOT IN sobre columna anulable vs NOT EXISTS

ingenua
SELECT c.ClienteId, c.Nombre
FROM dbo.Cliente c
WHERE c.Cedula NOT IN
      (SELECT e.Cedula FROM dbo.ClienteExterno e);
correcta
SELECT c.ClienteId, c.Nombre
FROM dbo.Cliente c
WHERE NOT EXISTS (SELECT 1 FROM dbo.ClienteExterno e
                  WHERE e.Cedula = c.Cedula);
  • Semántica: la ingenua pierde a los clientes 6 y 7 (Cedula NULL) porque NULL NOT IN (…) nunca es TRUE. No es diferencia de rendimiento: es diferencia de resultado.
  • Plan: NOT EXISTS se traduce directo a un Left Anti Semi Join. NOT IN sobre columnas anulables obliga a un plan más caro que además contabiliza la presencia de NULL del lado derecho. Cuando ambas columnas son NOT NULL, el optimizador demuestra la equivalencia y genera el mismo anti-join: ahí sí son intercambiables.
repro mínimo del daño
SELECT COUNT(*) FROM dbo.Cliente c
WHERE c.Cedula NOT IN (SELECT c2.Cedula FROM dbo.Cliente c2 WHERE c2.ClienteId IN (6,7));  -- 0

SELECT COUNT(*) FROM dbo.Cliente c
WHERE NOT EXISTS (SELECT 1 FROM dbo.Cliente c2
                  WHERE c2.ClienteId IN (6,7) AND c2.Cedula = c.Cedula);                   -- 10

UNION cuando bastaba UNION ALL

ingenua

WHERE Fecha <  '2023-01-01'

SELECT ClienteId, Fecha, Monto FROM dbo.VentaHist
WHERE Fecha >= '2023-01-01';

SELECT ClienteId, Fecha, Monto FROM dbo.VentaHist
WHERE Fecha <  '2023-01-01'
UNION ALL
SELECT ClienteId, Fecha, Monto FROM dbo.VentaHist
WHERE Fecha >= '2023-01-01';
UNIONUNION ALL

RiesgoSort spill a tempdb si la reserva se queda corta—

Patrón endémico en scripts que unen "histórico + incremental". Y si de verdad puede haber duplicados, la pregunta correcta no es "¿pongo UNION?" sino "¿por qué mi partición no es disjunta?".

§ 4

Errores silenciosos

15 casos · todos ejecutan sin error

Ninguno lanza excepción. Ese es exactamente el problema: el reporte sale, el proceso termina en verde y el número está mal.

1 · <> que esconde filas

SELECT COUNT(*) FROM dbo.Cliente WHERE Segmento <> 'RETAIL';  -- 6, no 9

fix · WHERE Segmento <> 'RETAIL' OR Segmento IS NULL, o IS DISTINCT FROM en 2022+.

2 · NOT IN con NULL → cero filas

fix · NOT EXISTS. Ver la comparación 3.3.

3 · Promedio con denominador equivocado

SELECT AVG(LimiteCredito) FROM dbo.Cliente;  -- divide entre 8, no entre 12

fix · decide explícitamente: AVG(ISNULL(LimiteCredito,0)) es otra pregunta, y hay que saber cuál estás respondiendo.

4 · SUM de conjunto vacío = NULL

SELECT (SELECT SUM(Cantidad) FROM dbo.Venta WHERE ClienteId = 11);  -- NULL, no 0

fix · ISNULL(SUM(…),0) en toda subconsulta escalar que alimente aritmética.

5 · COUNT(columna) cuando querías COUNT(*)

SELECT COUNT(*) AS Filas, COUNT(Canal) AS ConCanal FROM dbo.Venta;  -- 20 vs 17

6 · CHECK que no valida nada

fix · agregar IS NOT NULL a la condición o NOT NULL a la columna. Ver tema 4.

7 · UNIQUE que rechaza el segundo NULL (SQL Server)

fix · índice único filtrado WHERE Cedula IS NOT NULL. Ver tema 5.

8 · Concatenación que anula la fila entera

SELECT ClienteId, Ciudad + ' / ' + Segmento AS Ubic
FROM dbo.Cliente WHERE ClienteId IN (5,6);  -- NULL

fix · CONCAT() o ISNULL por componente. CONCAT_NULL_YIELDS_NULL OFF está deprecado: no es una solución.

9 · Espacios finales invisibles

SELECT ClienteId FROM dbo.Cliente WHERE Nombre = N'Ana Solis';     -- encuentra al 4 (padding ANSI)
SELECT ClienteId FROM dbo.Cliente WHERE Nombre LIKE N'Ana Solis';  -- no lo encuentra

fix · normaliza en la carga (TRIM), no en cada consulta.

10 · DISTINCT que colapsa por colación

fix · si el conteo de distintos es un KPI, fija la colación explícitamente en la consulta.

11 · TOP o paginación sin desempate

fix · termina siempre el ORDER BY con una columna única.

12 · ROW_NUMBER no determinista en deduplicación

fix · ídem. Es la causa raíz de reprocesos que "cambian" datos que nadie tocó.

13 · División entera silenciosa

SELECT COUNT(CASE WHEN Canal = 'WEB' THEN 1 END) / COUNT(*) AS PctWeb FROM dbo.Venta;  -- 0

fix · * 1.0 o CAST(… AS decimal(10,4)) antes de dividir.

14 · ISNULL que trunca

DECLARE @c varchar(3) = NULL;
SELECT ISNULL(@c,'ABCDEFG') AS ConIsNull,     -- 'ABC'  <- truncado al tipo del 1er argumento
       COALESCE(@c,'ABCDEFG') AS ConCoalesce; -- 'ABCDEFG'

15 · LEFT JOIN degradado a INNER por el WHERE

SELECT c.ClienteId, v.VentaId
FROM dbo.Cliente c
LEFT JOIN dbo.Venta v ON v.ClienteId = c.ClienteId
WHERE v.Canal = 'WEB';   -- elimina los clientes sin ventas: ya no es LEFT

fix · mover el predicado al ON, o WHERE (v.Canal='WEB' OR v.VentaId IS NULL). Nace del orden lógico: ON es paso 1, WHERE es paso 2. Es el puente al módulo 02.

§ 6

Mini-proyecto

conciliación semántica de clientes

Un archivo diario del buró llega con tipos y colación distintos a los del core: el escenario habitual de un staging alimentado por SSIS o por un COPY INTO. Nueve criterios de aceptación ejecutables, incluidos uno sobre el plan y uno de idempotencia.

Criterios de aceptación

cada consulta debe devolver OK
-- AC1 · Cardinalidad: universo sin duplicados
SELECT CASE WHEN COUNT(*) = COUNT(DISTINCT Cedula) THEN 'OK' ELSE 'FALLA' END
FROM dbo.ConciliacionClientes;

-- AC2 · Cuadre de conteos
SELECT CASE WHEN (SELECT COUNT(*) FROM dbo.ConciliacionClientes WHERE Estado <> 'SOLO_BURO')
               = (SELECT COUNT(*) FROM dbo.ClienteMasivo)
            THEN 'OK' ELSE 'FALLA' END;

-- AC3 · Null-safe: ambos NULL no es cambio
SELECT CASE WHEN COUNT(*) = 0 THEN 'OK' ELSE 'FALLA' END
FROM dbo.ConciliacionClientes
WHERE CiudadCore IS NULL AND CiudadBuro IS NULL AND CambioCiudad = 1;

-- AC4 · Null-safe inverso: NULL contra valor SÍ es cambio
SELECT CASE WHEN COUNT(*) = 0 THEN 'OK' ELSE 'FALLA' END
FROM dbo.ConciliacionClientes
WHERE ((CiudadCore IS NULL) <> (CiudadBuro IS NULL)) AND CambioCiudad = 0;

-- AC5 · Coherencia de Estado
SELECT CASE WHEN COUNT(*) = 0 THEN 'OK' ELSE 'FALLA' END
FROM dbo.ConciliacionClientes
WHERE (Estado = 'COINCIDE_IGUAL'  AND (CambioNombre = 1 OR CambioCiudad = 1))
   OR (Estado = 'COINCIDE_CAMBIO' AND  CambioNombre = 0 AND CambioCiudad = 0);

-- AC6 · Duplicados del buró colapsados
SELECT CASE WHEN COUNT(*) = 1 THEN 'OK' ELSE 'FALLA' END
FROM dbo.ConciliacionClientes WHERE Cedula = '0000000001001';

-- AC7 · La cédula que solo está en el buró
SELECT CASE WHEN Estado = 'SOLO_BURO' THEN 'OK' ELSE 'FALLA' END
FROM dbo.ConciliacionClientes WHERE Cedula = '9999999999001';

-- AC8 · Idempotencia (guarda un snapshot, reejecuta, compara en ambas direcciones)
SELECT CASE WHEN NOT EXISTS (SELECT * FROM dbo.ConciliacionClientes
                             EXCEPT SELECT * FROM dbo.Conciliacion_Snapshot)
             AND NOT EXISTS (SELECT * FROM dbo.Conciliacion_Snapshot
                             EXCEPT SELECT * FROM dbo.ConciliacionClientes)
            THEN 'OK' ELSE 'FALLA' END;

-- AC9 · Plan limpio: ninguna conversión implícita que afecte el plan
SELECT CASE WHEN CAST(p.query_plan AS nvarchar(max)) LIKE '%PlanAffectingConvert%'
            THEN 'FALLA' ELSE 'OK' END
FROM sys.dm_exec_query_stats qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) t
CROSS APPLY sys.dm_exec_query_plan(qs.plan_handle) p
WHERE t.text LIKE '%ConciliacionClientes%';

AC8 usa EXCEPT en las dos direcciones justamente porque es null-safe y compara filas completas. Es el idioma correcto para "estas dos tablas son idénticas" y evita el FULL JOIN con veinte ISNULL.

Pistas de diseño

  • La regla 3 obliga a resolver la diferencia de tipo del lado del archivo: convierte ClienteBuro.Cedula a varchar(13) en una tabla intermedia ya tipada — que es lo que harías en el staging real — en vez de dejar que el motor convierta la columna indexada del core.
  • La regla 4 pide ROW_NUMBER() OVER (PARTITION BY Cedula ORDER BY <criterio>, <columna única>). Sin la columna única final no hay idempotencia, y AC8 lo detecta.
  • El universo de claves se arma con FULL OUTER JOIN o con UNION de ambas claves: decide cuál y justifica el costo.
  • En un FULL JOIN, la única forma segura de saber si un lado faltó es preguntar por una columna NOT NULL de ese lado.

§ 8

Glosario técnico

términos usados en el módulo, agrupados por tema

Jerga de plan de ejecución, de lógica/modelado y de motores distintos a T-SQL, tal como aparece en las secciones de arriba. Escribe para filtrar.

Planes de ejecución y optimización

Index Seekplan

El motor usa la estructura ordenada del índice para saltar directo a las filas que cumplen el predicado, sin leer las que no aplican. Solo es posible cuando el predicado es SARGable. Tema 07e, comparación 3.1.

Index Scanplan

El motor recorre todo el índice o la tabla, fila por fila, y filtra después. Ocurre cuando el predicado no es SARGable: función o cálculo sobre la columna, conversión de tipo del lado equivocado, o colación distinta a la del índice.

SARGablepredicado

Search ARGument ABLE: un predicado que el optimizador puede usar directamente para limitar el recorrido del índice (Seek) en vez de evaluarlo fila por fila después de leer todo (Scan). Tema 07e.

Range through convertoptimizador

GetRangeThroughConvert: truco del optimizador para conservar el Index Seek pese a una conversión implícita, calculando el rango de valores de la columna que corresponde al literal convertido en vez de traducir cada fila. Solo funciona si la conversión no cambia el orden de clasificación — con colaciones Windows sí, con colaciones SQL heredadas no. Tema 07a.

PlanAffectingConvertwarning

Aviso que SQL Server agrega al plan (triángulo amarillo sobre el SELECT en SSMS) cuando una conversión implícita puede degradar el rendimiento. Se busca en el XML del plan con LIKE '%PlanAffectingConvert%'.

CONVERT_IMPLICITplan

Cómo aparece, en las propiedades de un operador del plan, la conversión de tipo que el motor insertó solo. Si está aplicada a la columna (no al literal), el predicado dejó de ser SARGable.

Predicate / Seek Predicateplan

Un plan distingue el filtro que definió el rango de un Seek (Seek Predicate, barato) del filtro evaluado fila por fila sobre lo ya leído (Predicate, residual). Ver el mismo filtro en el rol de Predicate es señal de que se está leyendo de más.

Predicate pushdownoptimizador

Reescritura que mueve un filtro lo más cerca posible del origen de los datos (antes de un join, dentro de una vista), reduciendo cuánto hay que procesar después. Es lo que separa el orden lógico (qué es correcto) del orden físico (cómo se ejecuta).

Hash Match (Aggregate)operador

Operador de plan que agrupa o deduplica filas construyendo una tabla hash en memoria. Aparece detrás de UNION, DISTINCT o GROUP BY cuando ningún índice entrega ya el orden necesario.

Sort spill (a tempdb)riesgo

Cuando un operador Sort o Hash necesita más memoria de la que el optimizador reservó, escribe a disco (tempdb) para terminar. Señal de una estimación de filas equivocada o de una reserva de memoria insuficiente.

Estadísticas / histogramaoptimizador

Resumen que el motor mantiene sobre la distribución de valores de una columna, usado para estimar cuántas filas cumplirán un predicado. Una función sobre la columna (YEAR(Fecha)) impide usarlo: la estimación se vuelve una conjetura fija.

DMVsistema

Dynamic Management View: vistas del sistema (sys.dm_exec_query_stats, sys.dm_exec_query_plan, …) que exponen el estado interno del motor. Sirven para cazar patrones como PlanAffectingConvert en todo el caché de planes.

Materializaciónconcepto

Forzar que un resultado intermedio se calcule y guarde por completo antes de seguir, en vez de dejar que el optimizador lo aplane dentro del plan general.

Lógica y modelado

UNKNOWNlógica

El tercer valor de la lógica de tres valores de SQL, junto a TRUE/FALSE. Cualquier comparación con NULL da UNKNOWN, y WHERE, HAVING, ON y el WHEN de un CASE descartan las filas en UNKNOWN, no solo las FALSE. Tema 04.

Multiconjuntoconcepto

Multiset: lo que realmente devuelve una consulta SQL. Admite filas duplicadas y no tiene orden intrínseco, a diferencia de un conjunto matemático. Tema 10.

Idempotentepropiedad

Una operación que produce el mismo resultado sin importar cuántas veces se ejecute. Un ROW_NUMBER sin desempate único no es idempotente: reprocesar el mismo archivo puede dejar una fila ganadora distinta a la de la vez anterior.

Binding (algebrización)fase

Fase donde el motor resuelve nombres, tipos, colaciones y permisos, antes de optimizar o ejecutar. Un alias del SELECT usado en el WHERE falla aquí, no en tiempo de ejecución.

Dependencia funcionalconcepto

Si una columna determina unívocamente el valor de otra (p. ej. la clave primaria determina cualquier otra columna de su fila), el motor puede permitir proyectarla sin agregarla ni incluirla en el GROUP BY. PostgreSQL lo aplica al agrupar por la clave primaria; T-SQL no.

Colaciones y comparación de texto

Colaciónconcepto

Collation: conjunto de caracteres, reglas de comparación y orden de clasificación de una columna de texto. Determina si dos cadenas se consideran iguales y en qué orden recorre un índice sobre ellas. Tema 08.

NULLS DISTINCT / NOT DISTINCTmodificador

Modificador de PostgreSQL 15+ para un índice o restricción UNIQUE: con NULLS DISTINCT (por defecto) admite varios NULL; con NULLS NOT DISTINCT replica el comportamiento de SQL Server, que solo admite uno.

Joins y acceso a datos

Anti-join / Semi-joinjoin

Un semi-join (EXISTS) devuelve las filas de un lado que tienen al menos una coincidencia del otro, sin duplicarlas aunque haya varias. Un anti-join (NOT EXISTS) devuelve las que no tienen ninguna. NOT IN sobre una columna anulable no es un anti-join limpio: puede devolver el conjunto vacío por culpa de un NULL.

Keyset paginationtécnica

Paginación que usa la última fila vista como filtro (WHERE (Nombre, ClienteId) > (@ultNombre, @ultId)) en vez de OFFSET, evitando releer las filas de páginas anteriores en cada página nueva. Módulo 10.

Cross-engine

Type coercionSpark

Nombre que usa Spark SQL para su propia lógica de conversión implícita de tipos, distinta de la lista de precedencia de SQL Server. Con spark.sql.ansi.enabled=true las conversiones inseguras lanzan error en vez de devolver NULL.

ShuffleSpark

Redistribuir datos entre particiones a través de la red para poder agruparlos o compararlos (p. ej. en un COUNT(DISTINCT …)). Es la operación más cara del motor; cualquier cosa que la fuerce de más es un problema de rendimiento real.
