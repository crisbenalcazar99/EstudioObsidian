Tabla de volumen (para los planes y el mini-proyecto)

Con 14 movimientos todo cabe en una página y cualquier frame parece gratis. dbo.MovimientoHist tiene 5 000 cuentas con 200 movimientos cada una, dos por día y con la misma FechaHora: así el costo y la divergencia ROWS/RANGE se ven a la vez. El índice IX_MovHist_POC sigue el patrón POC (Partition, Order, Covering) que viste en el módulo 03, tema 10: entrega las filas ya ordenadas para la ventana y evita el Sort.

T-SQL · volumen (~20 s)
CREATE TABLE dbo.MovimientoHist
(
    MovimientoId int           NOT NULL IDENTITY(1,1) CONSTRAINT PK_MovimientoHist PRIMARY KEY,
    CuentaId     int           NOT NULL,
    FechaHora    datetime2(0)  NOT NULL,
    Monto        decimal(14,2) NOT NULL
);

;WITH n AS (
    SELECT TOP (1000000) ROW_NUMBER() OVER (ORDER BY (SELECT NULL)) AS n
    FROM sys.all_objects a CROSS JOIN sys.all_objects b CROSS JOIN sys.all_objects c
)
INSERT dbo.MovimientoHist (CuentaId, FechaHora, Monto)
SELECT (n - 1) % 5000 + 1,                                                       -- 5 000 cuentas
       DATEADD(day, ((n - 1) / 5000) / 2, CAST('2024-01-01' AS datetime2(0))),   -- 2 mov/día: empates
       CAST(CASE WHEN n % 3 = 0 THEN -1 ELSE 1 END * ((n * 7) % 500 + 1) AS decimal(14,2))
FROM n;

CREATE NONCLUSTERED INDEX IX_MovHist_POC
    ON dbo.MovimientoHist (CuentaId, FechaHora, MovimientoId) INCLUDE (Monto);
GO

§ 1

Modelo mental

el tercer componente de OVER()

El módulo 03 cubrió partición y orden. Este módulo trata el tercer componente — el frame — que es justo donde viven los errores que no lanzan excepción: acumulados que saltan, medias que promedian de menos y "últimos valores" que son el actual.

Tres capas, tres preguntas

CapaPregunta que respondeSi la omites
PARTITION BY¿Con qué filas me comparo? (el universo)toda la tabla es una partición
ORDER BY¿En qué secuencia? y ¿quiénes son mis pares (filas con la misma clave de orden)?no hay secuencia ni pares; el frame es toda la partición
frame (ROWS / RANGE / GROUPS)Para esta fila, ¿qué subconjunto de la partición ve el agregado?RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW — con todo lo que eso implica (tema 3)
la idea centralEl frame se evalúa por fila. El motor recorre la partición ordenada y, en cada fila, pregunta "¿qué filas ve esta fila?". ROWS responde contando filas físicas; RANGE, comparando valores de la clave de orden; GROUPS, contando grupos de pares. Mismo SUM, tres preguntas distintas.

Quién usa el frame y quién lo ignora

FamiliaFunciones¿Respeta el frame?
AgregadosSUM, AVG, COUNT, MIN, MAX, STDEV, VAR…sí
ValorFIRST_VALUE, LAST_VALUE, NTH_VALUEsí — y por eso existe el error clásico de LAST_VALUE
RankingROW_NUMBER, RANK, DENSE_RANK, NTILEno (módulo 03, tema 3)
DesplazamientoLAG, LEADno: se mueven por filas, siempre
DistribuciónPERCENT_RANK, CUME_DISTno: miran toda la partición
PercentilesPERCENTILE_CONT / DISCno: en T-SQL ni siquiera admiten ORDER BY en el OVER

En SQL Server, escribir un frame en una función que no lo usa es un error de compilación ("The function 'LAG' may not have a window frame"). PostgreSQL lo acepta y lo ignora en silencio. Spark lo rechaza para las de ranking y desplazamiento.

Cómo lo ejecuta el motor

SQL Server · modo fila · lectura del plan de derecha a izquierda
Index Scan (ordenado) o Sort       -- filas en orden (partición, orden)
  -> Segment                        -- marca dónde empieza cada partición
  -> Segment / Sequence Project     -- marca grupos de pares y numera filas
  -> Window Spool                   -- materializa, por cada fila, las filas de su frame
  -> Stream Aggregate               -- agrega lo que dejó el spool
  • Window Spool en memoria: para frames ROWS cuyo tamaño máximo se conoce y no supera 10 000 filas. ROWS UNBOUNDED PRECEDING tiene además un atajo (fast-track): calcula el acumulado incrementalmente con dos filas por fila, sin releer el frame.
  • Window Spool en disco (worktable en tempdb): siempre con RANGE, y con ROWS cuando el frame puede superar 10 000 filas (por ejemplo UNBOUNDED FOLLOWING). Se delata en SET STATISTICS IO como Worktable con lecturas lógicas abultadas.
  • Window Aggregate (modo batch): un único operador que calcula en una pasada, sin spool. Disponible con columnstore desde 2016 y sobre rowstore desde 2019 (batch mode on rowstore, nivel de compatibilidad 150, Enterprise/Developer). Cuando aparece, la diferencia de costo ROWS/RANGE casi desaparece — la diferencia de resultado no.

otros motores

PostgreSQL

Nodo WindowAgg sobre un Sort. Para frames que se deslizan usa funciones de transición inversas (moving-aggregate, 9.4+): al avanzar resta la fila que sale y suma la que entra, en vez de recalcular el frame entero.

Spark SQL

Operador Window precedido de un shuffle por las columnas de partición y un sort dentro de cada partición. Sin PARTITION BY todo viaja a una sola tarea (aviso en el log, no error). Un frame con UNBOUNDED FOLLOWING obliga a bufferizar la partición completa en memoria: con skew eso termina en spill o en OOM.

Una partición, tres frames

cuenta 1 ordenada por FechaHora · la fila actual es la 5
fila  mov  FechaHora           grupo de pares
  1    1   2024-01-02 09:00    G1 ┐
  2    2   2024-01-02 09:00    G1 ┘
  3    3   2024-01-03 14:30    G2
  4    4   2024-01-05 10:00    G3 ┐
  5    5   2024-01-05 10:00    G3 │  <- fila actual
  6    6   2024-01-05 10:00    G3 ┘
  7    7   2024-01-08 11:15    G4

ROWS   BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW  -> filas 1..5   (para en la fila física)
RANGE  BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW  -> filas 1..6   (incluye a TODOS sus pares)
GROUPS BETWEEN 1 PRECEDING AND CURRENT ROW          -> filas 3..6   (su grupo y el anterior)

Lo que hay que retener: con RANGE, "fila actual" significa "valor actual", así que las filas 4, 5 y 6 ven exactamente lo mismo y devuelven el mismo acumulado. Si la clave de orden no tiene empates, ROWS y RANGE coinciden en resultado; nunca coinciden en costo dentro de SQL Server en modo fila.

Ingenua vs correcta

4 comparaciones con plan

Activa el plan real (Ctrl+M en SSMS) y SET STATISTICS IO, TIME ON;. Para no medir el render de un millón de filas en el cliente, cada par va envuelto en un agregado externo. Si tu instancia usa modo batch sobre rowstore, añade OPTION (USE HINT('DISALLOW_BATCH_MODE')) para ver el comportamiento en modo fila, que es el que tendrás en Standard o en compatibilidad < 150.

3.1 · frame por defecto

RANGE implícito vs ROWS explícito en un saldo corriente

ingenua · frame por defecto
SELECT COUNT(*) AS Filas, MAX(Saldo) AS SaldoMax
FROM (
    SELECT CuentaId, MovimientoId,
           SUM(Monto) OVER (PARTITION BY CuentaId
                            ORDER BY FechaHora) AS Saldo
    FROM dbo.MovimientoHist
) d;
correcta · ROWS + desempate único
SELECT COUNT(*) AS Filas, MAX(Saldo) AS SaldoMax
FROM (
    SELECT CuentaId, MovimientoId,
           SUM(Monto) OVER (PARTITION BY CuentaId
                            ORDER BY FechaHora, MovimientoId
                            ROWS UNBOUNDED PRECEDING) AS Saldo
    FROM dbo.MovimientoHist
) d;
IngenuaCorrecta
AccesoIndex Scan ordenado de IX_MovHist_POC, sin Sortigual: el índice POC entrega el orden en ambas
Operador de ventanaWindow Spool en disco + Stream AggregateWindow Spool en memoria (fast-track) + Stream Aggregate
STATISTICS IOWorktable con millones de lecturas lógicas (varias por fila)Worktable con 0 lecturas lógicas
ResultadoDistinto: los dos movimientos de cada día reciben el mismo saldo. SaldoMax sale menor porque el pico intradía desapareceUn saldo por movimiento, reproducible

Este par es la razón de la regla del tema 3: el default de SQL es a la vez el más caro y el que da el número equivocado cuando hay empates. Que el modo batch te salve el costo no te salva el saldo.

3.2 · join triangular

Subconsulta correlacionada vs ventana para un acumulado

El patrón anterior a 2012 que todavía aparece en procedimientos heredados. Se restringe a 500 cuentas (100 000 filas) para que la ingenua termine en un tiempo razonable.

ingenua · O(n²) por cuenta
SELECT COUNT(*), MAX(Saldo)
FROM (
    SELECT m.CuentaId, m.MovimientoId,
           (SELECT SUM(m2.Monto)
            FROM dbo.MovimientoHist m2
            WHERE m2.CuentaId = m.CuentaId
              AND (m2.FechaHora < m.FechaHora
                   OR (m2.FechaHora = m.FechaHora
                       AND m2.MovimientoId <= m.MovimientoId))
           ) AS Saldo
    FROM dbo.MovimientoHist m
    WHERE m.CuentaId <= 500
) d;
correcta · O(n) por cuenta
SELECT COUNT(*), MAX(Saldo)
FROM (
    SELECT CuentaId, MovimientoId,
           SUM(Monto) OVER (PARTITION BY CuentaId
                            ORDER BY FechaHora, MovimientoId
                            ROWS UNBOUNDED PRECEDING) AS Saldo
    FROM dbo.MovimientoHist
    WHERE CuentaId <= 500
) d;
IngenuaCorrecta
Forma del planNested Loops: por cada fila externa, un Index Seek en IX_MovHist_POC + Stream AggregateUn Index Seek de rango + Segment + Window Spool + Stream Aggregate
Filas procesadas200·201/2 = 20 100 por cuenta → ~10 millones100 000, una vez
Seek predicateSolo CuentaId y el rango de FechaHora; el OR del desempate queda como predicado residualRango de CuentaId

Fíjate en que la versión ingenua sí resolvía el desempate (con el OR): era correcta y lenta. La versión con ventana es correcta y rápida solo porque el ORDER BY incluye MovimientoId; sin él, sería rápida e incorrecta.

3.4 · percentiles

PERCENTILE_CONT como ventana + DISTINCT vs cálculo dirigido

Mediana de Monto por canal sobre dbo.VentaHist (1 000 000 de filas, 5 canales contando NULL). En SQL Server, PERCENTILE_CONT solo existe como función de ventana: produce un valor por fila que luego hay que colapsar.

ingenua · 1M filas para obtener 5
SELECT DISTINCT Canal,
       PERCENTILE_CONT(0.5)
         WITHIN GROUP (ORDER BY Monto)
         OVER (PARTITION BY Canal) AS Mediana
FROM dbo.VentaHist;
correcta · exacta, sin DISTINCT masivo
WITH o AS (
    SELECT Canal, Monto,
           ROW_NUMBER() OVER (PARTITION BY Canal ORDER BY Monto) AS rn,
           COUNT(*)     OVER (PARTITION BY Canal)                AS n
    FROM dbo.VentaHist
)
SELECT Canal, AVG(Monto * 1.0) AS Mediana
FROM o
WHERE rn IN ((n + 1) / 2, (n + 2) / 2)   -- 1 fila si n es impar, 2 si es par
GROUP BY Canal;
correcta · aproximada, SQL Server 2022 / Azure SQL
SELECT Canal,
       APPROX_PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY Monto) AS MedianaAprox
FROM dbo.VentaHist
GROUP BY Canal;
PERCENTILE_CONT + DISTINCTROW_NUMBER dirigidoAPPROX_PERCENTILE_CONT
Sort1M filas por (Canal, Monto)1M filas por (Canal, Monto)ninguno: agregado de un solo paso
Spoolsvarios Table/Window Spool sobre tempdb para contar la partición y localizar posicionesuno, para el COUNT(*) OVERninguno
Colapso finalHash o Sort Distinct sobre 1M filasGROUP BY sobre ≤ 10 filasnativo
Exactitudexacta, devuelve floatexacta, decimalaproximada, con error de rango acotado y documentado

El (n+1)/2, (n+2)/2 usa división entera a propósito: es la única división entera bienvenida de todo el curso. El caso NULL de Canal funciona porque PARTITION BY agrupa los NULL juntos (módulo 01, tema 5d); si lo resolvieras con un join a un GROUP BY por Canal, la fila NULL se perdería en el ON.

§ 4

Errores silenciosos

12 casos · ninguno lanza excepción

Todos compilan, todos terminan en verde y todos entregan un número que alguien va a poner en un reporte. Cada uno trae el caso mínimo sobre el dataset del §0.

1 · Saldo que se repite en movimientos simultáneos

SELECT MovimientoId, FechaHora, Monto,
       SUM(Monto) OVER (PARTITION BY CuentaId ORDER BY FechaHora) AS Acum
FROM dbo.Movimiento WHERE CuentaId = 1;   -- movs 4, 5 y 6 devuelven 800 los tres

fix · ORDER BY FechaHora, MovimientoId ROWS UNBOUNDED PRECEDING. Tema 3.

2 · Acumulado que cambia entre ejecuciones

SELECT MovimientoId,
       SUM(Monto) OVER (PARTITION BY CuentaId ORDER BY FechaHora
                        ROWS UNBOUNDED PRECEDING) AS Acum   -- ¿500 o -200 en el primer movimiento?
FROM dbo.Movimiento WHERE CuentaId = 1;

fix · ROWS sin desempate único es no determinista: el orden entre pares depende del plan (módulo 01, tema 9). Termina el ORDER BY en una columna única.

3 · LAST_VALUE que devuelve el valor actual

SELECT Sucursal, Fecha, Monto,
       LAST_VALUE(Monto) OVER (PARTITION BY Sucursal ORDER BY Fecha) AS "Ultimo"  -- = Monto
FROM dbo.VentaDiaria;

fix · ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING, o FIRST_VALUE con el orden invertido. Tema 7.

4 · El total que se volvió acumulado al agregarle ORDER BY

SELECT Sucursal, Fecha, Monto,
       100.0 * Monto / SUM(Monto) OVER (PARTITION BY Sucursal ORDER BY Fecha) AS PctDelTotal
FROM dbo.VentaDiaria;   -- el primer día de cada sucursal da 100 %

fix · el total de la partición no lleva ORDER BY. Si lo necesitas por otra razón, escribe ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING.

5 · Media móvil de "3 días" que promedia uno

SELECT Sucursal, Fecha,
       AVG(Monto) OVER (PARTITION BY Sucursal ORDER BY Fecha
                        ROWS BETWEEN 2 PRECEDING AND CURRENT ROW) AS Media3
FROM dbo.VentaDiaria;   -- el 2024-01-01 "media de 3" = 120, con una sola fila

fix · condicionar a COUNT(*) OVER (mismo frame) = 3. Tema 5.

6 · AVG sobre enteros que trunca

SELECT VentaId, Cantidad,
       AVG(Cantidad) OVER (ORDER BY VentaId ROWS BETWEEN 2 PRECEDING AND CURRENT ROW) AS Media
FROM dbo.Venta;   -- ventas 1-3: (1+2+1)/3 = 1, no 1.33

fix · AVG(Cantidad * 1.0) o CAST a decimal. En SQL Server AVG(int) devuelve int; en PostgreSQL devuelve numeric y en Spark double, así que el mismo código da números distintos en cada motor.

7 · "Día anterior" que en realidad es hace tres días

SELECT Fecha, Monto,
       LAG(Fecha) OVER (PARTITION BY Sucursal ORDER BY Fecha) AS FechaAnt,
       Monto - LAG(Monto) OVER (PARTITION BY Sucursal ORDER BY Fecha) AS VarVsDiaAnterior
FROM dbo.VentaDiaria WHERE Sucursal = 'GYE';   -- el 08 se compara con el 05

fix · densificar contra dbo.Calendario antes de la ventana (tema 10) o validar DATEDIFF(day, FechaAnt, Fecha) = 1.

8 · LAG con default 0 que fabrica una variación

SELECT Sucursal, Fecha, Monto,
       Monto - LAG(Monto, 1, 0) OVER (PARTITION BY Sucursal ORDER BY Fecha) AS Variacion
FROM dbo.VentaDiaria;   -- el primer día "creció" 120 respecto de nada

fix · el default debe significar algo del negocio (un saldo inicial sí; un cero inventado no). Si no hay periodo anterior, la variación es NULL. Y el default solo se usa fuera de la partición, nunca para reemplazar un NULL real. Tema 6.

9 · Ventana calculada antes de densificar

WITH v AS (
    SELECT Sucursal, Fecha,
           SUM(Monto) OVER (PARTITION BY Sucursal ORDER BY Fecha
                            ROWS BETWEEN 2 PRECEDING AND CURRENT ROW) AS Suma3
    FROM dbo.VentaDiaria
)
SELECT c.Fecha, v.Suma3
FROM dbo.Calendario c
LEFT JOIN v ON v.Sucursal = 'GYE' AND v.Fecha = c.Fecha
WHERE c.Fecha BETWEEN '2024-01-01' AND '2024-01-14';
-- el 08 sigue sumando 04+05+08, y los días 06, 07, 10 salen NULL

fix · el calendario se une antes de la ventana, en el mismo FROM donde se calcula. Tema 10.

10 · Filtro en WHERE que recorta la historia de la ventana

SELECT MovimientoId, FechaHora,
       SUM(Monto) OVER (PARTITION BY CuentaId ORDER BY FechaHora, MovimientoId
                        ROWS UNBOUNDED PRECEDING) AS Saldo
FROM dbo.Movimiento
WHERE CuentaId = 1 AND FechaHora >= '2024-01-05';   -- el "saldo" arranca de cero el día 5

fix · WHERE se evalúa antes que la ventana (módulo 03, tema 2). Calcula la ventana sobre toda la historia en una CTE y filtra fuera. Solo es seguro filtrar dentro si el filtro coincide con la partición.

11 · "Mediana" con PERCENTILE_DISC en un conjunto par

SELECT DISTINCT
       PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY x) OVER () AS Cont,   -- 25
       PERCENTILE_DISC(0.5) WITHIN GROUP (ORDER BY x) OVER () AS Disc    -- 20
FROM (VALUES (10),(20),(30),(40)) t(x);

fix · la mediana estadística de un conjunto par es CONT. DISC devuelve un valor que existe en los datos — útil para montos reales, incorrecto si el reporte dice "mediana". Tema 8.

12 · Ventana sin PARTITION BY en Spark (costo silencioso)

-- Databricks: compila, corre y manda toda la tabla a UNA tarea
SELECT movimiento_id,
       sum(monto) OVER (ORDER BY fecha_hora, movimiento_id
                        ROWS UNBOUNDED PRECEDING) AS acumulado_global
FROM movimiento_hist;
-- log: "No Partition Defined for Window operation! Moving all data to a single partition..."

fix · si el negocio admite partición (por cuenta, por día), úsala. Si de verdad necesitas un acumulado global sobre millones de filas, calcula acumulados por bloque y súmales el offset de los bloques anteriores en un segundo paso.

-- AC1 · Densidad: cada cuenta tiene una fila por día, sin huecos
SELECT CASE WHEN COUNT(*) = 0 THEN 'OK' ELSE 'FALLA' END
FROM (SELECT CuentaId FROM dbo.SaldoDiarioCuenta
      GROUP BY CuentaId
      HAVING COUNT(*) <> DATEDIFF(day, MIN(Fecha), MAX(Fecha)) + 1
          OR MIN(Fecha) <> '2024-01-01' OR MAX(Fecha) <> '2024-04-09') x;

-- AC2 · Unicidad de la clave
SELECT CASE WHEN COUNT(*) = COUNT(DISTINCT CONCAT(CuentaId, '|', Fecha)) THEN 'OK' ELSE 'FALLA' END
FROM dbo.SaldoDiarioCuenta;

-- AC3 · Cuadre contra la fuente: saldo final = inicial + todos los movimientos
SELECT CASE WHEN COUNT(*) = 0 THEN 'OK' ELSE 'FALLA' END
FROM dbo.CuentaProy c
JOIN dbo.SaldoDiarioCuenta s ON s.CuentaId = c.CuentaId AND s.Fecha = '2024-04-09'
CROSS APPLY (SELECT ISNULL(SUM(m.Monto), 0) AS Total
             FROM dbo.MovimientoProy m WHERE m.CuentaId = c.CuentaId) t
WHERE s.SaldoCierre <> c.SaldoInicial + t.Total;

-- AC4 · Continuidad: cierre = anterior + neto, en todas las filas
SELECT CASE WHEN COUNT(*) = 0 THEN 'OK' ELSE 'FALLA' END
FROM dbo.SaldoDiarioCuenta
WHERE SaldoCierre <> SaldoAnterior + Neto OR SaldoAnterior IS NULL;

-- AC5 · Días sin movimiento: tantos como (días densos - días con movimiento)
SELECT CASE WHEN
   (SELECT COUNT(*) FROM dbo.SaldoDiarioCuenta WHERE NumMov = 0 AND Neto = 0)
 = (SELECT COUNT(*) FROM dbo.SaldoDiarioCuenta)
 - (SELECT COUNT(*) FROM (SELECT DISTINCT CuentaId, CAST(FechaHora AS date) AS d
                          FROM dbo.MovimientoProy) z)
 THEN 'OK' ELSE 'FALLA' END;

-- AC6 · Media de 7 días: NULL exactamente en los 6 primeros días de cada cuenta…
SELECT CASE WHEN COUNT(*) = 0 THEN 'OK' ELSE 'FALLA' END
FROM dbo.SaldoDiarioCuenta
WHERE (Media7Neto IS NULL) <> (Fecha < '2024-01-07');
-- …y coincide con un cálculo independiente, sin ventanas, para una cuenta con huecos
SELECT CASE WHEN COUNT(*) = 0 THEN 'OK' ELSE 'FALLA' END
FROM dbo.SaldoDiarioCuenta s
CROSS APPLY (SELECT ISNULL(SUM(m.Monto), 0) / 7.0 AS Ref
             FROM dbo.MovimientoProy m
             WHERE m.CuentaId = s.CuentaId
               AND m.FechaHora >= DATEADD(day, -6, s.Fecha)
               AND m.FechaHora <  DATEADD(day,  1, s.Fecha)) r
WHERE s.CuentaId = 7 AND s.Media7Neto IS NOT NULL
  AND ABS(s.Media7Neto - r.Ref) > 0.01;

-- AC7 · PERCENT_RANK coherente por día
SELECT CASE WHEN COUNT(*) = 0 THEN 'OK' ELSE 'FALLA' END
FROM (SELECT Fecha FROM dbo.SaldoDiarioCuenta
      GROUP BY Fecha
      HAVING MIN(PctRankDia) <> 0 OR MAX(PctRankDia) > 1) x;

-- AC8 · Idempotencia: guarda un snapshot, reejecuta el procedimiento, compara en ambas direcciones
-- SELECT * INTO dbo.SaldoDiario_Snapshot FROM dbo.SaldoDiarioCuenta;  EXEC dbo.uspSaldoDiario;
SELECT CASE WHEN NOT EXISTS (SELECT * FROM dbo.SaldoDiarioCuenta EXCEPT SELECT * FROM dbo.SaldoDiario_Snapshot)
             AND NOT EXISTS (SELECT * FROM dbo.SaldoDiario_Snapshot EXCEPT SELECT * FROM dbo.SaldoDiarioCuenta)
            THEN 'OK' ELSE 'FALLA' END;

-- AC9 · Ningún RANGE en el procedimiento (heurística sobre el texto)
SELECT CASE WHEN OBJECT_DEFINITION(OBJECT_ID('dbo.uspSaldoDiario')) LIKE '%RANGE%'
            THEN 'FALLA' ELSE 'OK' END;

AC6 es el criterio que importa: compara el resultado de la ventana con una suma por rango de fechas que no sabe nada de filas ni de frames. Si densificaste después de la ventana, o usaste ROWS 6 PRECEDING sobre la serie con huecos, la cuenta 7 lo delata.

Pistas de diseño

  • Orden de las CTE: serie (cuenta × calendario) → neto diario (GROUP BY CuentaId, CAST(FechaHora AS date)) → LEFT JOIN de ambas → ventanas. Agregar antes de unir evita multiplicar filas (módulo 02, tema 10).
  • CAST(FechaHora AS date) en el GROUP BY es aceptable aquí porque recorres la tabla completa; no lo uses como filtro en un WHERE sobre una tabla grande (módulo 01, tema 7e).
  • Con la serie ya densa, "últimos 7 días calendario" es exactamente ROWS BETWEEN 6 PRECEDING AND CURRENT ROW, y el NULL de los primeros días sale de COUNT(*) OVER (mismo frame) < 7.
  • SaldoAnterior es LAG(SaldoCierre, 1, SaldoInicial): un default con significado de negocio. Necesitas SaldoCierre materializado en una CTE previa porque no se pueden anidar funciones de ventana.
  • DiaMaxSaldo: FIRST_VALUE(Fecha) OVER (PARTITION BY CuentaId ORDER BY SaldoCierre DESC, Fecha ROWS UNBOUNDED PRECEDING). El Fecha en el orden es el desempate que convierte "un día de máximo" en "el primero".
  • Para AC8, crea dbo.SaldoDiarioCuenta con DROP + SELECT … INTO o TRUNCATE + INSERT; ambos son idempotentes si el cálculo es determinista. Los efectos de cada opción en el log se ven en el módulo 12.
